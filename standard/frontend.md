# Стандарт фронтенда

Версия определяется соседним файлом [VERSION](VERSION).

## 1. Область применения и смысл требований

Стандарт предназначен для клиентских веб-приложений с отдельным backend. Он задаёт границы ответственности, согласованность данных, устройство UI и критерии проверки. Для сайта без авторизации или серверного состояния неприменимые разделы отмечаются с объяснением; инфраструктура ради них не добавляется.

**Обязательно** — свойство, которое должна обеспечивать реализация. **Рекомендуется** — способ достижения этого свойства; эквивалентное существующее решение допустимо. Примеры названий файлов и инструментов не становятся обязательными требованиями.

Для нового проекта применяются все относящиеся к нему требования с начала разработки. В существующем проекте фиксируются расхождения и объём модернизации. Подключение документа не означает, что весь проект уже соответствует ему. Новые и изменяемые компоненты соблюдают стандарт в границах задачи; локальная правка не должна незаметно превращаться в переписывание приложения.

Инструкции владельца и согласованные требования продукта имеют приоритет. Принятые альтернативы и исключения описываются рядом с копией стандарта, с причиной и областью действия. Неизвестное состояние не считается соответствием.

## 2. Рекомендуемые технологии

| Задача | Рекомендация | Для чего |
|---|---|---|
| UI | React + TypeScript strict | Компоненты и явные типы данных/состояний |
| SPA build | Vite | Dev server, HMR, production assets |
| Серверное состояние | TanStack Query | Кэш, запросы, отмена, обновление после записи |
| Стили | Tailwind CSS + semantic tokens | Общая тема и стили состояний |
| Primitives | shadcn-подход и Radix | Контролируемые исходники и готовая механика взаимодействия |
| Маршруты | React Router | URL, навигация и границы экранов |
| Сложные формы | React Hook Form + Zod | Валидация, dirty/pending/error |
| Иконки | Один согласованный набор, например Lucide | Единый визуальный язык |
| API-типы | Генерация из поддерживаемой OpenAPI-схемы | Сокращение ручного дублирования DTO |
| Проверки | TypeScript, ESLint, unit runner, Playwright | Статика, логика и пользовательские сценарии |

Версии выбираются совместно с учётом Node, браузеров и существующих зависимостей, фиксируются lockfile. Наличие другой библиотеки не требует замены, если обязательные свойства обеспечены. Выбор SSR, другого framework или особых требований продукта оценивается отдельно: не переделывать их в SPA для формального совпадения.

Таблицы, графовые библиотеки, редакторы и прочие специализированные зависимости добавляются по потребности. Приватный пакет допустим при доступной процедуре установки для разработчика и CI, но стандарт его не требует.

## 3. Границы ответственности

```text
Экран → query/mutation → API-функция → HTTP → backend
   ↓          ↓
общий UI   серверный кэш
```

- **Транспорт:** авторизация, сериализация, HTTP-ошибки, отмена, ограниченные повторы.
- **API-функции:** endpoint, параметры и типы предметного ресурса.
- **Queries:** ключи, условия загрузки, свежесть и получение данных.
- **Mutations:** пользовательское действие и согласованность представлений после записи.
- **Экран:** композиция сценария, состояния интерфейса и навигация.
- **Общие UI-компоненты:** внешний вид, тема, клавиатура, фокус и взаимодействие без зависимости от страницы.

Авторизация и сырой `fetch` не размещаются в JSX-компонентах. При этом отдельный custom hook на каждый вызов не обязателен: `useQuery` с общими query options может быть достаточен. Не создавать обёртки, которые только увеличивают число переходов между файлами.

Подходящая структура: `api/`, `queries/`, `mutations/`, `components/ui/`, `components/layout/`, `pages/`. Эквивалентна организация внутри `features/<feature>/`. Важна ответственность, а не совпадение папок. Большие экраны разделяются на понятные части; пустые заготовки и механическое дробление не нужны.

Глобальный provider добавляется для сквозной ответственности. Порядок providers определяется зависимостями. Экземпляр query client стабилен в течение сессии приложения. Локальное состояние не поднимается в глобальный context без потребности.

### 3.1. Организация модулей и зависимости

**Обязательно:**

- Между модулями нет циклических зависимостей. Общие UI-компоненты и инфраструктура не импортируют конкретные страницы или функциональные модули продукта. Экран может связывать их для реализации сценария.
- Предметные правила, расчёты и преобразования имеют понятное место и не поддерживаются в независимых копиях на разных экранах. Они могут находиться внутри функционального модуля; отдельный domain-слой для простого CRUD не требуется. Backend независимо проверяет правила, влияющие на целостность данных и доступ.
- У выделенного функционального модуля есть понятная ответственность и согласованный набор экспортов для потребителей. Другие модули используют этот интерфейс, а не его внутренние детали. Отдельный `index.ts` в каждой папке не обязателен.
- Новые слои и абстракции вводятся для конкретной ответственности или повторяемой проблемы с учётом стоимости поддержки. Наличие архитектурного шаблона само по себе не обосновывает дополнительные файлы и зависимости.

**Рекомендуется:**

- По мере роста приложения группировать код по функциям продукта, например `features/orders/` и `features/users/`. В небольшом приложении структуры из раздела 3 может быть достаточно.
- Компоненты, запросы, преобразования и тесты, специфичные для одной функции, держать рядом с ней. В общий слой переносить код, когда понятна общая ответственность; внешнего сходства фрагментов недостаточно для создания универсальной абстракции.
- Существенные архитектурные решения кратко описывать в документации проекта: выбранный подход, причина, ограничения и условия пересмотра. Отдельный реестр решений и документ на каждую локальную правку не нужны.

FSD, Clean Architecture, repository/use case-слои и фиксированное дерево папок не обязательны. При проверке оцениваются ответственность модулей, направление зависимостей и соблюдение их интерфейсов, а не названия каталогов. Существующее приложение не перестраивается целиком при локальной задаче; обнаруженные расхождения фиксируются и исправляются в согласованном объёме.

### 3.2. Архитектурное решение нового приложения

**Обязательно:** до реализации первого пользовательского сценария определить и кратко зафиксировать архитектуру приложения на основе требований продукта. Выбор стека и создание дерева папок сами по себе архитектурным решением не являются.

Решение охватывает согласованный объём разработки и отвечает на следующие вопросы:

| Вопрос | Что фиксируется |
|---|---|
| Какие сценарии реализуются? | Основные действия пользователя, экраны и значимые ограничения: доступ, объём данных, интеграции и требования к платформе, если они есть |
| Как разделена ответственность? | Функциональные модули, назначение каждого, владельцы предметных правил и данных; экран и модуль не обязаны соответствовать друг другу один к одному |
| Как связаны модули? | Направление зависимостей, используемые интерфейсы и место композиции сценариев, затрагивающих несколько модулей |
| Где живёт состояние? | Серверные данные, черновики, локальное состояние, URL, сессия и предпочтения — по разделам 4–8, только для используемых видов состояния |
| Как подключены сквозные механизмы? | Точки подключения транспорта, роутера, providers, общей темы и UI; предметные детали не переносятся в инфраструктуру ради переиспользования |
| Как проходит основной сценарий? | Путь от маршрута и действия пользователя через модуль до обновления представлений, включая API, если он используется; границы ошибок и проверки сценария |

**Рекомендуется:** для клиентского приложения с отдельным backend начинать с одного приложения с внутренними модулями и явными зависимостями. В небольшом CRUD достаточно экранов, общего UI и слоя данных. Несколько самостоятельных областей продукта удобно группировать в функциональные модули. Отдельный слой предметной логики полезен, когда сложные правила используются независимо от экранов; он не вводится автоматически. Микрофронтенды и отдельные пакеты не являются способом по умолчанию: для них нужна конкретная потребность, например независимые поставки частей приложения, с оценкой стоимости интеграции.

Для небольшого приложения достаточно нескольких абзацев, схемы зависимостей или таблицы модулей и примерной структуры в `adoption.md`. Если решение объёмное, допустим существующий документ архитектуры со ссылкой из `adoption.md`. Отдельный файл, диаграмма и набор ADR не обязательны. Неизвестные условия и предположения отмечаются явно; блокирующие продуктовые решения выясняются до реализации зависящей от них части. Все будущие функции заранее не проектируются.

При реализации решение уточняется по фактическому коду. Изменение границ модулей, владельца состояния или существенной зависимости отражается в записи; перенос отдельного файла не требует нового архитектурного документа. Одно подключение стандарта без задачи на реализацию не требует придумывать архитектуру. При аудите существующего приложения оцениваются фактические границы; отсутствие такой записи само по себе не доказывает дефект его реализации.

### 3.3. Исходная модель и взаимодействие модулей

**Рекомендуемый пример** для приложения с несколькими функциональными областями:

```text
src/
  app/                    # Запуск, providers, роутер и композиция приложения
  pages/                  # Экраны и композиция пользовательских сценариев
  features/
    orders/               # UI, API, queries/mutations и правила заказов
    customers/            # UI, API, queries/mutations и правила клиентов
  components/
    ui/                   # Общие контролы без предметных зависимостей
    layout/               # Общие элементы компоновки
  api/                    # Общий транспорт, не API всех предметных ресурсов
  theme/                  # Токены и применение общей темы
```

Это исходная модель, а не обязательный шаблон. Создаются только используемые части. В компактном приложении API-функции и query options могут находиться в общих `api/` и `queries/`, как в разделе 3. При функциональной организации они остаются рядом со своим модулем. DTO предметного ресурса принадлежат его API-слою; UI-модели и преобразования размещаются у потребителя. Общий тип выделяется, когда у нескольких потребителей действительно один контракт, а не только одинаковые поля.

Направление зависимостей: композиция приложения связывает экраны и providers; экран использует функциональные модули и общий UI; функциональный модуль использует общий UI и инфраструктуру. Запрос внутри модуля проходит через его API-функцию к общему транспорту. Предметные расчёты по возможности независимы от React и HTTP и проверяются отдельно. Общие части не импортируют экраны и функциональные модули.

Сценарий нескольких модулей собирается на экране или в отдельной функции/hook этого сценария, если композиция достаточно сложна. Прямая зависимость одного функционального модуля от другого допустима через согласованный интерфейс без цикла; она отражается в архитектурном решении. Например, форма заказа может использовать публичный выбор клиента, при этом модуль клиентов не зависит от заказов. Перенос такой связи в глобальный store или шину событий только ради устранения прямого импорта не требуется.

Для ресурса, используемого несколькими модулями, определяется один владелец API-контракта и правил согласованности серверного кэша. Потребители используют его query options, ключи или эквивалентный интерфейс вместо независимых копий данных. Это не требует единого глобального модуля для всех ресурсов. Последствия записи для других представлений определяются по разделу 6.

### 3.4. Проверка архитектурного решения

**Обязательно:** после реализации первого сквозного сценария сопоставить решение с фактическим кодом. Должно быть понятно, где добавить следующий аналогичный экран, запрос или предметное правило и какие части от этого зависят.

Проверить по реализованному сценарию:

- У каждого задействованного модуля понятна ответственность, а импорты соответствуют выбранному направлению зависимостей и интерфейсам.
- Можно проследить путь от маршрута и действия пользователя до обновления UI, включая API и ошибки, если они есть в сценарии. Экран не содержит транспортную авторизацию, а общая инфраструктура — предметную композицию.
- Для используемых данных, черновиков и URL-состояния определены владельцы; независимые копии серверного состояния не создаются.
- Общая тема и UI применяются через предусмотренные точки подключения; проверки разделов 9 и 11 выполнены в объёме сценария.

Достаточно адресной проверки кода и сценария; новый анализатор зависимостей или CI-framework ради этого пункта не нужен. Наличие схемы и каталогов без рабочего сценария не подтверждает архитектуру. На этой стадии проверяется реализованный объём, а не готовность всех будущих функций.

## 4. Владение состоянием

| Состояние | Место |
|---|---|
| Данные сервера | Query cache или эквивалентный слой серверного состояния |
| Составная форма | Form library; простая форма может использовать локальный state |
| Открытие панели, временный выбор | Локальное состояние |
| Фильтры, сортировка, страница для ссылок и Back/Forward | URL |
| Предпочтения отображения | Хранилище с явно выбранной областью: браузер или аккаунт |
| Сессия и доступные действия | Auth-слой |

Не поддерживать независимую копию серверного списка в локальном state. Черновик редактируемой сущности допустим: определить момент его создания и реакцию на новый серверный ответ так, чтобы не потерять пользовательский ввод.

## 5. Получение данных и кэш

Ключ запроса включает параметры, влияющие на результат: идентификатор, фильтры, страницу и организацию/workspace, если от них зависит ответ. Списки, детали и несовместимые представления различаются. Переиспользовать фабрики ключей при чтении и инвалидировании.

Для обычных JSON-совместимых объектов TanStack Query уже учитывает свойства независимо от их порядка; собственная рекурсивная сортировка/хэширование не нужны без отдельной причины. Порядок массива значим. См. [Query Keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys).

| Механизм | Назначение |
|---|---|
| `staleTime` | Срок, пока данные считаются свежими |
| `gcTime` | Срок хранения неиспользуемого кэша |
| `refetchInterval` | Периодическое получение данных |
| Обновление кэша / инвалидирование | Реакция на известное изменение |
| Refetch по фокусу/подключению | Обновление при событии |

`staleTime` не задаёт частоту polling. Значения выбираются по сценарию и цене запросов. Polling прекращается для завершённых операций и неактивных представлений, где он не нужен. См. [Important Defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

Передавать `AbortSignal` до HTTP-вызова. Отмена не показывается как пользовательская ошибка. Повторы ограничены; недействительная авторизация и отказ в доступе не должны создавать бесконечные запросы. Временные ошибки и ограничение частоты обрабатываются с учётом backend.

При смене пользователя отменять прежние запросы и очищать персональный кэш. Контексты организаций/workspaces изолируются ключами либо явным сбросом. Поздний ответ старой сессии не должен попадать в новую. UI не заменяет серверную проверку доступа.

## 6. Запись и обновление представлений

Мутация представляет законченное пользовательское действие и может включать несколько запросов. Если требуется атомарность, её обеспечивает backend. Последовательность HTTP-запросов на клиенте сама по себе транзакцией не является; для частичного успеха нужно понятное поведение.

После успеха полный свежий ответ можно записать в точный detail-кэш. Представления, которые нельзя достоверно восстановить из ответа, инвалидируются: например, отфильтрованные списки и агрегаты. Только что обновлённый detail не перезапрашивается без причины; всё приложение не инвалидируется при каждом сохранении.

Если сценарий требует свежий список до завершения действия, дождаться обновления. Иначе допустимо фоновое обновление. Успех записи и ошибка последующего чтения различаются: не предлагать повторить уже выполненную операцию из-за неудачного refetch.

Автоматический повтор записи допускается только при безопасной семантике backend. Оптимистическое обновление применять при заметной пользе и понятном rollback; обновления после ответа часто достаточно.

## 7. Транспорт, типы и streaming

Общий транспорт сохраняет HTTP-статус, машинный код и идентификатор запроса, если они доступны. Пользователь получает понятное сообщение; диагностические детали доступны без раскрытия токенов и приватных payload.

При token-based авторизации refresh согласует параллельные запросы и ограничивает повторы. Другие схемы авторизации допустимы; стандарт не требует Bearer-токены. Операцию нельзя повторять автоматически, не разобравшись с риском двойного запуска.

Если backend поддерживает OpenAPI, генерировать DTO из актуальной схемы. Codegen из старого файла не актуализирует API. Ручные DTO при неполной схеме остаются в API-слое и отмечаются как ограничение. UI-модели могут отличаться и иметь явное преобразование. Не скрывать несовместимость через `any`.

TypeScript не валидирует JSON во время выполнения. Runtime-валидация добавляется там, где недоверенные или нестабильные данные создают реальную проблему.

Если используется SSE/streaming, определить:

- проверку HTTP-статуса до чтения потока;
- поведение при истечении сессии;
- отмену и освобождение ресурсов;
- различение успеха, серверной ошибки и обрыва;
- однократное завершение обработчика;
- поддерживаемый формат событий и политику переподключения.

Отдельный streaming helper не наследует автоматически правила JSON-клиента. Переподключение к операции и повторный запуск операции должны различаться.

## 8. Маршруты и доступ

Маршруты и навигация имеют согласованный источник определения. Реестр с path, label, layout и capability — подходящая реализация, но не обязательная надстройка над любым router.

Route guard управляет UI; backend независимо проверяет чтение и изменение ресурсов. Проверки отдельных действий внутри экрана допустимы: доступ к странице не даёт права на все кнопки.

Предусмотреть прямые ссылки, Back/Forward, неизвестный маршрут, отказ доступа и восстановление сессии. Секреты не передаются в URL.

## 9. UI, темы, формы и доступность

Переиспользовать общие кнопки, поля, диалоги, меню, badges и layout-компоненты. Поведение фокуса, клавиатуры и overlay не копируется по страницам. В shadcn-подходе исходники принадлежат проекту, поэтому их изменения и совместимость поддерживает команда проекта.

Все новые компоненты изначально учитывают тему по требованиям этого раздела, даже при единственной продуктовой теме. Конкретные палитры, шрифты и переключатели стандартом не задаются.

Semantic tokens и общие варианты компонентов — основной способ поддерживать единый UI. Tailwind рекомендован. Небольшой CSS допустим для анимаций, сложных селекторов и интеграций, когда он упрощает поддержку. Динамические координаты и размеры допустимы в inline styles/CSS variables. Статические inline styles и произвольные значения не должны создавать параллельную дизайн-систему.

RHF + Zod рекомендованы для составных форм с валидацией. Для небольшого поля допустим локальный state. Нужны:

- предотвращение повторного submit и понятное состояние выполнения;
- сохранение черновика при ошибке;
- ошибки поля рядом с полем и общая ошибка формы;
- первая загрузка, пустой результат, ошибка, повторная попытка там, где она осмысленна;
- сохранение полезных данных при фоновом обновлении.

Radix не гарантирует доступность готового экрана автоматически. Обязательны подписи, имя icon-only кнопок, видимый фокус, работа с клавиатуры, возврат фокуса после диалога и сообщение об ошибках. Статус обозначается дополнительно к цвету. Проверяются узкий экран, масштабирование и reduced motion. См. [Radix Accessibility](https://www.radix-ui.com/primitives/docs/overview/accessibility).

### 9.1. Что закладывается с начала разработки

Все новые UI-компоненты должны получать оформление через общую систему темы с первого дня, даже если продукт пока поставляется с одной темой. Это обязательное архитектурное требование.

Количество тем, переключатель, каталог шрифтов и пользовательские настройки — отдельные продуктовые возможности. Для готовности к темам они не нужны. Нужны общие токены, правила их применения и проверка, что изменение темы достигает всего интерфейса.

Если сначала закрепить цвета и шрифты внутри страниц, позднее добавление переключателя изменит только часть UI. Потребуется переделывать состояния контролов, всплывающие элементы и интеграции. Поэтому механизм темы входит в спецификацию базовых компонентов, а каждый новый компонент сразу соблюдает его.

### 9.2. Как тема влияет на компоненты

```text
Определение темы
    ↓
Семантические токены на корневом элементе
    ↓
Общие UI-компоненты и стили состояний
    ↓
Экраны, таблицы и портальные элементы

Для SVG/canvas и сторонних библиотек:
токены → небольшой адаптер → обновление отрисовки
```

Тема задаёт значения. Компонент выбирает семантическую роль: поверхность, текст, граница, акцент, ошибка, фокус. Экран компонует компоненты.

Компоненты не должны знать названия тем, проверять их через `if` или иметь собственные копии палитры. Обычному DOM-компоненту достаточно CSS-переменных и классов, связанных с ними; подписка каждого компонента на React context не требуется. Context или другой общий механизм нужен для управления выбором и интеграций, которым необходимо явно обновить рисунок.

Рекомендуемая реализация для описанного стека — CSS custom properties на `<html>`, отображённые в Tailwind utilities. Допустима эквивалентная система, обеспечивающая те же свойства. Формат значения токена должен быть единым: полные CSS-цвета и наборы HSL-каналов нельзя смешивать без адаптера.

### 9.3. Какие свойства принадлежат теме

Минимальный набор определяется используемыми компонентами:

| Группа | Что должно управляться централизованно |
|---|---|
| Поверхности | Фон приложения, карточки, всплывающие поверхности |
| Текст | Основной, вторичный, текст на акцентном фоне |
| Взаимодействие | Акцент, выделение, границы полей, фокус |
| Состояния | Ошибка, предупреждение, успех, недоступность |
| Типографика | Семейства шрифтов по назначению, общая шкала размеров и межстрочных интервалов |
| Геометрия | Общие радиусы, тени и применяемая шкала отступов |
| Специальные поверхности | Sidebar, заголовки и закреплённые ячейки таблиц — когда такие элементы есть |

Не каждое свойство обязано отличаться между темами. Не нужно заранее создавать токен для каждого CSS-свойства. Новый токен вводится, когда существующая роль не выражает требуемый смысл или повторяющееся оформление.

Тема должна предоставлять все используемые значения — напрямую или через явно определённую базовую тему. Изолированные переопределения на страницах не должны случайно менять общий смысл токенов.

Фиксированные цвета допустимы для пользовательских цветов данных, иллюстраций и образцов палитры. Это явные исключения, которые проверяются на читаемость. Цвета категорий данных не следует автоматически заменять акцентом интерфейса.

### 9.4. Состояния и составные компоненты

Тематизация охватывает не только исходное состояние элемента:

- normal, hover, active/pressed и focus-visible;
- selected/checked/open;
- disabled и read-only;
- invalid/error;
- loading, если у него есть отдельное оформление.

Компонент использует согласованные пары фона и текста. Менять фон, оставляя случайный фиксированный цвет текста, недостаточно.

| Компонент | Требование |
|---|---|
| Кнопка | Фон, текст, граница и все состояния получают значения из темы |
| Поле | Текст, placeholder, фон, граница, фокус и ошибка согласованы |
| Select/combobox | Trigger, меню, варианты и выделение используют ту же тему, включая портальную часть |
| Dialog/popover/tooltip/toast | Поверхность, текст, граница, тень и overlay учитывают тему |
| Таблица | Заголовки, строки, выделение, hover, pinned-ячейки, редакторы и меню настроек учитывают тему |
| Иконка | Обычно наследует цвет текста; собственный цвет задаётся по смысловой роли |
| График/диаграмма | Оси, подписи, фон и tooltip учитывают тему; цвета данных имеют отдельные правила |

Новый primitive считается завершённым после проверки его используемых состояний. Отдельная страница не должна исправлять оформление primitive для каждой темы.

### 9.5. Шрифты как часть механизма

Шрифты задаются по назначению, а не по имени конкретного семейства внутри компонента. Обычно достаточно основного текста и технического текста; роли заголовков, кнопок и полей добавляются, когда продукту нужно управлять ими отдельно. Роли могут по умолчанию ссылаться на одно семейство.

Назначение определяется функцией элемента: trigger выпадающего поля может быть HTML-кнопкой, но типографически относится к полю. Явная техническая роль не должна случайно сбрасываться общими стилями кнопки или поля.

Смена семейства не должна обрезать подписи и ломать строки таблиц. Учитываются реальные метрики шрифта, начертания, межстрочный интервал и fallback для кириллицы, цифр и специальных знаков. Наличие названия семейства в CSS не означает, что его файл доступен.

Гарантированное начертание требует поставки разрешённых к распространению файлов либо явно заявленной зависимости от системных шрифтов. Загрузка шрифта может потребовать повторного измерения таблицы или диаграммы. Конкретные семейства и возможность выбора пользователем этим стандартом не задаются.

### 9.6. Наследование, порталы и сторонние библиотеки

Область глобальной темы должна охватывать всё приложение и места монтирования порталов. Переменные только на вложенном `App`-контейнере не достигают меню, вынесенного в `body`.

Если предусмотрена локальная тема вложенной области, её портальные элементы должны сохранять ту же область оформления: через соответствующий portal container или явную передачу значений. Локальная тема не требуется, если её нет в продуктовом сценарии.

Для стороннего компонента сначала используется его штатная поддержка темы или CSS-переменных. При несовместимом формате создаётся небольшой адаптер. Не размещать переопределения библиотеки по множеству страниц.

Canvas, iframe, генераторы SVG и некоторые графические библиотеки не получают оформление обычным наследованием DOM. Им передаются вычисленные значения и сигнал обновить отрисовку. При изменении шрифта учитывается и возможная необходимость пересчитать геометрию.

Экспорт имеет явную политику: повторяет экранное оформление либо использует оформление документа. Запись имени шрифта в SVG сама по себе не встраивает файл шрифта. Экспорт проверяется отдельно от UI.

### 9.7. Применение и смена темы

Базовая тема должна работать без пользовательских настроек и доступа к хранилищу.

Если продукт поддерживает выбор оформления:

1. Определяется один источник активного выбора и понятный порядок приоритетов: defaults, системные предпочтения и явный выбор пользователя — в той комбинации, которая нужна продукту.
2. Значения восстанавливаются до первого отображения интерфейса, насколько позволяет платформа. Первый кадр и поведение при недоступном хранилище проверяются.
3. Изменение применяется ко всем элементам, включая уже открытые меню и диалоги.
4. Смена оформления не перемонтирует бизнес-экран, не сбрасывает форму, фокус, фильтры или положение пользователя в сценарии.
5. Область сохранения — браузер или аккаунт — определяется продуктом. Серверная синхронизация и синхронизация вкладок не подразумеваются автоматически.

Цветовая палитра, светлый/тёмный режим и типографика должны иметь явные правила сочетания. При независимой настройке изменение одного параметра не сбрасывает другие. Не создавать все комбинации заранее: реализуются только заявленные продуктом режимы. Приоритет CSS определяется явно, без случайной зависимости от порядка загрузки файлов.

### 9.8. Проверка готовности к темам

Даже при одной продуктовой теме нужна ранняя проверка заменяемости значений. Для неё достаточно временно подставить заметно отличающиеся токены и шрифт в демонстрационный экран или тестовую fixture. Вторую тему не требуется публиковать пользователям.

| Проверка | Критерий |
|---|---|
| Изменение токенов поверхности, текста и акцента | Общие компоненты обновляются без правки их исходников |
| Hover, focus, selected, disabled, error | Нет остатков прежней палитры и потери читаемости |
| Уже открытые меню, диалог, tooltip | Оформление совпадает с остальным UI |
| Замена шрифта и длинный русский текст | Нет обрезанных подписей и сломанной компоновки |
| Таблица со scroll/pinned и редактором | Закреплённые поверхности непрозрачны, состояния согласованы |
| График или иной renderer, если используется | Обновляются оформление и необходимые размеры |
| Смена темы при заполненной форме | Черновик и пользовательский контекст сохраняются |
| Первая загрузка и недоступное хранилище, если есть выбор | Рабочий fallback, отсутствие падения |
| Экспорт, если затронут | Соблюдается его заявленная политика оформления |

Проверяются представители семейств и рискованные интеграции. Полный перебор всех шрифтов и экранов не нужен. Поиск фиксированных цветов и `font-family` помогает найти обходы темы, но не заменяет проверку итогового интерфейса.

**Критерий реализации:** новый компонент уже учитывает тему. Формулировка «тематизацию добавим потом» не соответствует этому стандарту. Пользовательский переключатель и дополнительные темы могут появиться позже без переработки базовых компонентов.

## 10. Таблицы и производительность

Сложные таблицы используют общий адаптер выбранной библиотеки: согласованные настройки колонок, overflow, плотность, сортировку и область сохранения предпочтений. Маленькая статичная таблица может быть обычной HTML-таблицей.

Большие списки требуют решения о серверной пагинации и при необходимости виртуализации. Смена шрифта не должна ломать измерения, закреплённые колонки и обрезку текста. Портальные редакторы и меню тоже учитывают тему.

До оптимизации измеряются начальный bundle и критические сценарии. Тяжёлые необязательные разделы могут загружаться отложенно. Не добавлять `memo`, code splitting и библиотеки только ради формального пункта аудита. Полезны бюджеты производительности, привязанные к реальным ограничениям продукта.

## 11. Проверки

| Изменение | Отправная точка |
|---|---|
| Документация | Факты, ссылки, кодировка, diff |
| Логика | Typecheck/lint и затронутые unit-тесты |
| Экран/форма | Статика и пользовательский сценарий |
| Транспорт, auth, кэш | Проверка поведения границы, ошибок и смены контекста |
| Выпуск | Production build, критические сценарии собранного приложения, bundle budget и smoke артефакта |

Обязательные CI-gates проекта сохраняются. Не повторять одну сборку через несколько вложенных команд без необходимости. Пропуски и блокировки окружением называются явно.

ESLint проверяет правила кода и импортов; unit-тесты — функции и поведение обработчиков/кэша; компонентные или короткие browser tests — взаимодействие; E2E — критические пути через реальные границы; визуальная проверка — компоновку.

Не требовать конкретного JSX в конкретном файле: перенос в дочерний компонент без изменения поведения не должен ломать тест. Regex-проверки допустимы для узких осмысленных запретов, AST/ESLint предпочтительнее для правил кода. Новый test framework вводится по потребности.

Retry не делает тест детерминированным. Нужны изолированные данные, контролируемые ответы и ожидание состояния вместо фиксированных пауз. Для тем проверять представителей семейств и рискованные интеграции по требованиям раздела 9, без полного перебора всех экранов и шрифтов.

## 12. Воспроизводимое окружение и выпуск

Репозиторий указывает поддерживаемую версию Node, package manager, lockfile, доступ к приватным зависимостям, переменные окружения без секретных значений и требования тестового API/БД. CI использует совместимое окружение. Непроверенную версию не объявлять поддерживаемой.

Установка из lockfile выполняется при подготовке окружения или изменении зависимостей. Нужны браузеры Playwright и системные зависимости, если используются browser tests. Команды документируются для поддерживаемой ОС; POSIX-присваивания и `.venv/bin/python` не выдаются за готовые PowerShell-команды.

Production assets SPA раздаёт выбранный web server/CDN. Определяются fallback клиентских маршрутов, API routing, кэширование HTML и версионированных assets, конфигурация endpoint. `vite preview` применяется для проверки сборки, а не production-раздачи. Клиентские переменные сборки публичны, секреты туда не помещаются. См. [Vite deployment](https://vite.dev/guide/static-deploy.html).

Проверка dev server не заменяет проверку production-артефакта. Наличие npm-script не подтверждает его успешный запуск. Merge, push и deploy выполняются в пределах поручения пользователя и правил проекта.

## 13. Пример сквозного сценария

Редактирование названия сущности:

1. Экран получает список через query с параметрами фильтра в ключе.
2. Форма создаёт черновик, проверяет непустое значение и вызывает mutation.
3. API-функция отправляет PATCH через общий транспорт; pending блокирует повторный submit.
4. При отказе API форма сохраняет текст и показывает ошибку.
5. Полный свежий ответ обновляет detail-кэш. Отфильтрованные списки инвалидируются, поскольку название могло изменить их состав и порядок.
6. После успеха форма закрывается. Ошибка обновления списка сообщается отдельно от уже успешной записи.

Проверка: изменить название и увидеть новое значение; при отказе API увидеть сохранённый черновик и ошибку. Смена тестовых токенов во время редактирования меняет оформление, сохраняя введённый текст. Конкретные endpoint и библиотечные методы определяются проектом.

## 14. Критерий завершения

Реализован согласованный сценарий с нужными состояниями; данные согласованы; доступ проверяет backend; компоненты учитывают тему и доступны; подходящие проверки выполнены, ограничения названы. Для нового приложения архитектурное решение сопоставлено с кодом первого сквозного сценария по разделу 3.4. Небольшого отчёта с результатами достаточно. Дополнительные контракты, универсальные framework и многоступенчатые ревью не требуются.
