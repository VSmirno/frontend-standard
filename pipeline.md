# Пайплайн применения стандарта

## 1. Что подключается к проекту

У каждого элемента своя задача:

- [Единый стандарт](standard/frontend.md) определяет требования, включая механизм тем.
- Skill `frontend-standard` задаёт процедуру нового проекта, аудита и модернизации.
- Блок в `AGENTS.md` закрепляет требования для дальнейших задач.
- Проверки подтверждают результат; наличие файлов само по себе не доказывает соответствие.

После подключения рекомендуемая структура прикладного репозитория:

```text
AGENTS.md
docs/
  standards/frontend/
    VERSION
    frontend.md
    adoption.md
  frontend-audit.md           # После аудита
  frontend-modernization.md   # Когда требуется план работ
```

Аудит и план не создавать пустыми при первоначальном подключении. Они появляются по задаче. Для нескольких самостоятельных приложений допустимы отдельные области и отчёты; дублировать стандарт для каждого экрана не нужно.

## 2. Установка или обновление по запросу в чате

Пользователь передаёт агенту адрес репозитория и просит прочитать README, установить либо обновить и переустановить skill. Клонирование, получение выбранной редакции, сборку пакета и файловые операции выполняет агент. Пользователь не запускает команды и не копирует файлы.

Порядок установки определён в [README.md](README.md), в разделе «Инструкция агенту: установка / обновление / переустановка». В установленной папке копия README находится рядом с этим pipeline. Не запускать Python или другие installer-скрипты.

По умолчанию skill устанавливается для пользователя; проектная установка выполняется по явному запросу. При переустановке прежний каталог целиком сохраняется вне области обнаружения skills. Проверяются конечный состав, версия и источник.

## 3. Редакции и доступность ресурсов

Агент использует актуальную main после fetch либо явно выбранный пользователем выпуск и указывает точный SHA установки. Обновление skill не меняет версию, принятую прикладным проектом.

В исходном репозитории требования находятся в standard/. В установленном skill комплектная копия находится в references/standard/. Для аудита уже подключённого проекта приоритет имеет его закреплённая редакция. При первом подключении фиксируется версия из комплекта skill и источник установки.

Прочитать SKILL.md прямо из checkout тоже можно; это не регистрирует его автоматически. После установки пользователь вызывает $frontend-standard на следующем ходе; если клиент не обнаружил skill, требуется новая сессия.

## 4. Закрепление стандарта в проекте

Агент или разработчик выполняет:

1. Проверить текущие инструкции, документы и наличие ранее принятой версии.
2. Скопировать содержимое `standard/` выбранного выпуска в `docs/standards/frontend/`. Существующий каталог сначала сравнить; не перезаписывать молча.
3. Создать `adoption.md` по [шаблону](templates/adoption.md): версия, источник выпуска, область, реальные проектные решения.
4. Добавить блок из [AGENTS.frontend.md](templates/AGENTS.frontend.md) к существующему AGENTS.md. Сохранить остальные инструкции, адаптировать пути при другой структуре. Не дублировать уже существующий блок.
5. Проверить доступность ссылок и зафиксировать эти изменения в обычном порядке проекта.

Если пользователь просил только аудит, копирование файлов и изменение AGENTS.md не обязательны: можно проверить по явно указанному внешнему выпуску и записать его в отчёт. Если стандарт отсутствует и версия не указана, использовать комплектную редакцию skill для аудита с явным указанием источника, без молчаливого принятия её проектом.

Подключение фиксирует правила последующих изменений. Состояние всего существующего кода выясняется аудитом. Не писать «проект соответствует» после одного копирования документов.

## 5. Новый проект

Команда:

> Используй $frontend-standard. Подключи стандарт к этому проекту, закрепи его в AGENTS.md и реализуй минимальный рабочий сценарий из требований продукта. Тематизация должна работать с самого начала; пользовательские темы и переключатель без отдельного требования не добавляй.

Результат:

- закреплённая редакция и проектные решения;
- архитектурное решение по разделу 3 закреплённого стандарта, сопоставленное с кодом первого сквозного сценария;
- необходимая основа общего UI и темы;
- слои данных, маршрутизации и доступа только в объёме сценария;
- рабочий сценарий и подтверждённые проверки.

Для одного подключения:

> Подключи стандарт и инструкции к репозиторию. Реализацию приложения пока не начинай.

## 6. Аудит существующего проекта

Команда:

> Используй $frontend-standard. Проведи аудит текущего фронтенда по закреплённому стандарту. Подготовь docs/frontend-audit.md и приоритетный план в docs/frontend-modernization.md. Исходный код пока не меняй. Разделяй дефекты, допустимые альтернативы и непроверенное.

Агент проверяет все применимые области стандарта, а визуальные сценарии выбирает репрезентативно. В отчёте связывает семейства UI с общими реализациями, потребителями и проверенными состояниями; выборку обосновывает сценариями и рисками. Сравнивает текущий код с ревизией прежней приёмки, отдельно отмечает новые и непроверенные части. Выводы подтверждает кодом, командами или наблюдениями; dependencies и CSS variables сами по себе не доказывают соответствия.

Отчёт использует [шаблон audit](templates/audit.md). Статусы: соответствует, частично, не соответствует, не применимо, не проверено. У расхождения есть последствие, доказательство и необходимое действие. Общий процент соответствия не нужен.

План по [шаблону modernization](templates/modernization.md) группирует работы по общей причине и указывает зависимости. Срочность определяется риском для данных, доступа и пользователя, затем распространённостью дефекта. Несовпадение названия библиотеки не является самостоятельной причиной миграции.

## 7. Модернизация

Команда:

> Используй $frontend-standard. Выполни план docs/frontend-modernization.md в согласованном объёме. Сохрани предметное поведение. После реализации проверь результат по плану, исправь недоделанное и обнови аудит. Публикацию и деплой выполняй только если они отдельно поручены.

Для ограниченного объёма указать конкретные задачи плана. Если поручен весь план, агент не должен останавливаться после первого блока только ради промежуточного подтверждения. Объективные блокировки сообщаются отдельно, независимая работа продолжается.

Обычный порядок для тем: общие токены → primitives и состояния → порталы/адаптеры → экраны → проверка. Для API или кэша порядок зависит от обнаруженного дефекта. Результат проверяется один раз по выполненному объёму; найденные проблемы исправляются и адресно перепроверяются. Не запускается бесконечный цикл общего ревью.

В конце остаётся актуальный аудит: какие обязательные расхождения закрыты, какие приняты как исключения, что ещё не проверено. Частичный результат не называется полным соответствием.

## 8. Обычная разработка после внедрения

AGENTS.md направляет агента к требованиям при последующих задачах. Полный skill-аудит не нужен для каждой кнопки. Предыдущая приёмка не распространяется автоматически на новый экран; изменение общего компонента требует адресной проверки затронутых композиций у потребителей. Изменяемый компонент соблюдает тему, состояния, границы данных и подходящие проверки.

Инструкции агента не гарантируют автоматическое соблюдение. Повторяемые машинно проверяемые правила закрепляются существующими линтерами и тестами по мере необходимости; поведение и визуальная целостность проверяются сценариями. Новый CI не создаётся без отдельной потребности.

## 9. Обновление стандарта

1. Сравнить новую редакцию с принятой проектом.
2. Выделить реальные изменения обязательных требований и оценить их влияние.
3. По поручению обновить копию `standard/`, VERSION и историю adoption; сохранить проектные решения отдельно.
4. Обновить аудит только затронутых областей и план необходимых работ.

Не обновлять принятые требования до `latest` при каждом запуске skill. Skill другой версии тоже должен работать от закреплённых документов. При несовместимости процедуры явно сообщить её и использовать подходящий выпуск, без скрытой подмены.

## 10. Приёмка самого skill

Формальная проверка включает frontmatter, ссылки, ресурсы и оба варианта размещения. Она не доказывает поведение агента. При пилотном использовании нужны три наблюдаемых сценария:

- Новый проект: подключение не затирает AGENTS.md, архитектура определена до реализации и сопоставлена с первым сценарием по разделу 3 принятой редакции, тема работает до появления пользовательского переключателя.
- Аудит: эквивалентная библиотека не признаётся дефектом, непроверенное отмечается, исходный код не меняется.
- Модернизация: исправлен согласованный объём, критерии проверены, остаток явно зафиксирован.

При изменении процедуры дополнительно использовать ограниченный пример со старой приёмкой и новым экраном: агент связывает семейства UI с реализацией и потребителями, выбирает сценарии по состояниям/рискам, отделяет исторические результаты от текущих доказательств. В примере успешная запись с отказом обновления списка и запись при активном поиске помогают проверить целостность пользовательского действия. Native HTML не должен автоматически приводить к замене библиотеки; отсутствие runtime отмечается как ограничение, а не успешный тест.

Достаточно одного реального пилотного проекта и адресных примеров для непокрытых режимов. Дорабатывать skill по фактическим ошибкам; не добавлять правила для гипотетических случаев.
